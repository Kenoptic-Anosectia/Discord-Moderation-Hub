## Provenance and parser boundary

`tests/fixtures/logger/message_events.json` is one small pack containing **six invented cases**: partial content absent, explicit empty content, embed-only update, no cached message, single delete, bulk delete. IDs 101/102 (messages), 201 (channel), 301 (guild) are arbitrary tiny test sentinels, not sourced from Discord. Text is explicitly SYNTHETIC. There are no usernames, attachments, credentials, private/ticket content or real IDs. `prior_cache` is a minimal setup summary, **not** a complete Serenity `Message` or the application's `CachedMessage`; no author is fabricated by filling missing metadata. For future handler tests that need a known author, construct a synthetic cache entry explicitly (e.g. sentinel 401 and label `SYNTHETIC author`, no avatar). The pack is not a production ingestion format.

`tests/logger_fixture_shapes.rs` deserializes each `event` directly into actual public `serenity::model::event::{MessageUpdateEvent, MessageDeleteEvent, MessageDeleteBulkEvent}`; cache setup embeds also use actual `Embed`, IDs use actual `MessageId`. It imports no application handler and implements no copied logger. The envelope uses serde `deny_unknown_fields`; checks cover unique nonempty names, SYNTHETIC provenance/cache text, duplicate cache IDs and raw content-shape consistency. Serenity's own unknown-event-field acceptance is intentionally not overridden; this is not a comprehensive Discord protocol validator or a privacy scanner.

Public cached source inspected: `serenity-0.12.5/src/model/event.rs:513–603` (bulk/single/update Deserialize definitions), `:605–684` (update application); `src/client/dispatch.rs:300–318` (event-to-FullEvent mapping). `Cargo.toml` permits 0.12.4 but **Cargo.lock resolves 0.12.5**, as the offline build confirms. These references are dependency-source paths, not application paths.

* Update `content: Option<String>` preserves missing versus `""` (`None` versus `Some("")`). Missing versus JSON null **collapses** to `None`; the raw `serde_json::Value` distinguishes them before conversion. A real handler receiving only typed `FullEvent` cannot recover that raw distinction. Do not assert otherwise or add a raw gateway hook just for this tranche.
* `embeds: Option<Vec<Embed>>` preserves omission versus `[]`. Null also collapses to `None`. The executable check covers omission versus empty array; no separate null-embeds test is claimed.
* Some fields, e.g. `webhook_id`, have `deserialize_some` and nested Option: omission `None`, explicit null `Some(None)`. The executable test demonstrates this contrast, not a universal rule for all nested Options.
* Delete wire `id` maps to `MessageDeleteEvent.message_id`; bulk wire `ids` maps to its vector. `FullEvent` renames these to `deleted_message_id` / `multiple_deleted_messages_ids`. We test event model deserialization, **not** construction/dispatch of actual FullEvents.
* The fixtures have no full old/new Serenity message snapshots. Actual dispatch can supply `old_if_available` and `new` using Serenity's cache independently of the bot's own cache. Future tests must vary both, not assume `new` always exists.

## Smallest proposed seam (NOT implemented by A05)

In a separately authorized implementation, move the **existing three message match arms**, not a rewritten simulation, into private async handler functions callable from `event_handler` and colocated Rust unit tests. Keep handlers private so integration-test API exposure is unnecessary. Pass only own-cache reference, configured log-channel ID, existing FullEvent fields, a `LogSink`, and a clock. `event_handler` remains a thin delegate; role, ticket and staff age-command branches remain untouched. Own cache can remain the existing `Arc<RwLock<HashMap<...>>>` with a freshly constructed synthetic instance per test; no database/config loading is necessary.

`LogSink` should accept the exact `CreateMessage`/destination assembled by the real handler (including synthetic generated embed-file bytes) and return a small structured outcome/error. A single production adapter replaces calls in `log_to_channel` and `log_to_channel_with_files`; a recording fake queues success/403/429/pending outcomes and captures call order and serialized builders. Existing dependencies suffice: boxed std Future/Pin or generic async closure, no new macro/runtime crate. Add an explicit application timeout around the adapter future; test it using an injected deadline/sleep abstraction, not real waiting. Sanitize error reporting at the boundary: operation, error category, retryability and bounded attempt count; no content, embed JSON, tokens or raw HTTP bodies. Record local diagnostics, not a recursive send into the failed log channel.

Use an injected `now_ms`/timestamp provider for payload timestamps. Later audit tests additionally need an `AuditSource` and fake sleep/time functions around the real lookup/retry helpers. Freeze returned entries and ordering; record calls. Do not implement an audit subsystem, fake logger or new persistence in this fixture card.

This seam alone must first characterize current ordering/errors; behavior corrections then need their own failing handler tests and authorization. A recording fake proves the real handler requested a send, not Discord delivery. No app timeout/retry numbers below are represented as existing guarantees.
