# BUMP-POLICY - bump confirmation and reminder-cycle policy (pure)

Card BU1. Module `src/bump/{mod,policy}.rs` - pure, Discord-free core of the Bump Buddy replacement. No serenity type, no I/O, no clock read, no randomness; `now` (unix seconds) and every id are passed in.

API: `decide(&MessageFacts, &BumpConfig, &State, now) -> Decision::{Confirmed(Confirmation{message_id, confirmed_at, next_due}) | Ignored(IgnoreReason)}`; `observe(..) -> (Decision, State)` (state changes only on Confirmed); `reminder_status(&State, &BumpConfig, now) -> NoCycle|NotYet|Due|AlreadyReminded` and `due(..) -> bool`; `State::{confirmed, reset(now), reminded}`; validated `BumpConfig::new(guild, bot, marker, interval_secs)` and `parse_interval_secs(Option<&str>)`.

Rules enforced: a message confirms only if it is not a webhook, is in the configured guild, its author id equals the listing-bot id, the author is a bot account, its id is non-zero and newer than the last confirmed id, and `content` or `embeds_text` contains the marker. Users, other bots, webhooks, other guilds, DMs, and replies without the marker (cooldown/error) are ignored and leave the state untouched. A repeated or older message id is ignored (idempotent). The reminder is `due` from `last_confirmed_at + interval` until `State::reminded` is applied, then not again until the next confirmation or `State::reset(now)` (restarts the cycle from `now`, keeps the last message id so an old message cannot undo it). Time arithmetic saturates. Ignore reasons and config errors are enum codes; config errors name the key and never carry the value.

Interval bounds enforced by `BumpConfig::new`: 600..=86400 s (default 7200). Marker: non-blank, at most 200 bytes, no control characters.

Config keys (READ by the wiring card, not by this module): `BUMP_BOT_ID` - no default, unset = feature off, 0 refused; `BUMP_SUCCESS_MARKER` - `Bump done`, an invalid marker (empty/blank/control/over 200 bytes) refuses the config; `BUMP_INTERVAL_SECS` - `7200`, `parse_interval_secs` refuses anything but plain digits within 600..=86400. The card lists no guild key; `BumpConfig` takes `guild_id` and the wiring card must supply it (the error label `BUMP_GUILD_ID` is a placeholder).

Assumptions (Bump Buddy's real behaviour is unknown; conservative choices): marker match is a case-sensitive substring; `interaction_name` and `channel_id` are carried but not used by the decision (no channel or command filter here; the plan's channel restriction belongs to wiring/config); the 2 h default is the listing bot's public cooldown, unverified; message ids are assumed to increase over time (snowflakes); only the last confirmed id is remembered; `due` uses the interval of the config passed in, not the one in force at confirmation; an `AtMostOnce` send policy (mark reminded before sending) is the caller's job.

Tested (31 unit tests in `src/bump/policy.rs`): confirmation from the listing bot (embed and content); user, other bot, user with the bot's id, webhook (same and different id), cooldown/error text, wrong guild, DM, id 0 ignored; duplicate and older ids; cooldown reply leaves the due time unchanged; due flips exactly at the boundary; one reminder per cycle; new confirmation reopens it; manual reset (with and without a prior cycle, dedupe kept); saturation; interval/marker/id config bounds and hostile interval spellings; no value in errors; a seeded LCG sequence test against a model runtime (60 seeds x 400 steps) checking at most one reminder per cycle and no silence once overdue. RED evidence: commit `7f41d1b` (types and stubs, no logic) ran 31 tests: 30 failed, 1 passed (`config_errors_do_not_echo_the_value`, trivially true for a stub that always refuses).

NOT done: no runtime (nothing posts, pings or schedules), no commands (`/bump status|reset`), no persistence of `State`, no Discord registration, no `config.rs`/`.env.example`/`main.rs` wiring beyond the `mod bump;` line; `#![allow(dead_code)]` in `src/bump/mod.rs` is temporary and W1 removes it.
