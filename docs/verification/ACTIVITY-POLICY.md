# ACTIVITY-POLICY - activity accounting policy (pure)

Card AC1. Module `src/activity/{mod,policy}.rs` - pure, Discord-free core.

`activity::policy::account_message(&MessageEvent, &ActivityConfig) -> MessageOutcome`
(`Counted(Increment)` | `Ignored(IgnoreReason)`) and
`activity::policy::Ledger::apply_voice(&VoiceEvent, &ActivityConfig) -> VoiceOutcome`
(`sessions` + `anomalies`), plus `Ledger::note_restart(now_at, last_heartbeat_at, cfg)`.
No serenity type, no I/O, no clock read, no randomness; every timestamp and id is passed in.

Rules it enforces:
- One message gives +1 for the key (UTC day, user, channel). The event type has NO content field, so content cannot be read or stored.
- Bots, excluded channels and zero ids are ignored on the message path (reason codes: `BotAuthor`, `ExcludedChannel`, `InvalidUser`/`InvalidChannel`/`InvalidGuild`, checked in that order). On the voice path an event naming a zero guild, user or channel is refused whole and flagged `UnaccountedChannel`: no session is opened or closed and the ledger is left as it was.
- Voice: join opens, leave and move close, a state update in the same channel only changes the self-deaf flag. AFK and excluded channels are not credited; the `UnaccountedChannel` anomaly is raised on the outcome that DROPS the session, not on the one that opened it.
- Self-deafened time counts only when `count_self_deafened` is true (wiring default false). A flag change mid-session splits the stretch, so only the deafened part is dropped.
- A session crossing UTC midnight is split into one record per day; each record lies inside one day.
- A closed session whose stretches touch more than `MAX_SESSION_RECORDS` (366) UTC days in total is not credited and is flagged `UnaccountedChannel`. The count is an upper bound computed by arithmetic, not a walk, so a refused span never allocates.
- Duplicate join (`DuplicateUpdate`), out-of-order update (`OutOfOrderUpdate`), channel mismatch (`ChannelMismatch`) and missing old state (`MissingOldState`) raise an anomaly and credit nothing.
- Restart: every open session closes at `min(last_heartbeat_at, now_at)` - never past the restart instant, so a heartbeat that claims a moment after the restart credits nothing that had not happened yet. The difference is `RestartGap` and is not credited (crediting offline hours would inflate levels).
- All time is injected. `day_start` and `next_day_start` saturate, so a timestamp at either edge of `i64` cannot panic; `utc_day` uses integer division only and clamps a timestamp outside `YYYY-MM-DD` to `9999-12-31`.

Assumptions (the spec was silent): the `at` field is seconds since the Unix epoch; `utc_day` is `YYYY-MM-DD`; a text message in the AFK channel IS counted (AFK is a voice concept); a move whose old state is unknown opens a session in the NEW channel only; a voice event that names the id zero is refused even when its other ids are valid (the id zero is not a real guild, member or channel); `MAX_SESSION_RECORDS` is 366 (a year of days), far beyond any real voice presence.

Config keys (READ by the wiring card, not by this module; this module reads no env var and no file, so the parsing rules below are a REQUIREMENT for that card, not behaviour this module enforces):
`ACTIVITY_MODE` default `off` (the wiring card must keep an unrecognised value off); `ACTIVITY_EXCLUDED_CHANNEL_IDS` default empty (empty => nothing excluded; the wiring card must fail the whole key closed on a malformed entry rather than drop the entry); `ACTIVITY_AFK_CHANNEL_ID` default unset (unset => no AFK channel); `ACTIVITY_COUNT_SELF_DEAFENED` default `false` (false => self-deafened time is not credited).

Tested: 87 unit tests in `src/activity/policy.rs`. RED evidence round 1: commit `2deca4e` ran the suite with a non-functional scaffold - 9 passed, 23 failed (the 9 that passed are the ones the type definitions alone satisfy: config validation, config error hygiene, anomaly code stability, the counter sum and the empty-session sweep). Then implemented in `3a5964d`. RED evidence round 2: commit `29e3aec` added the edge-of-range and restart-bound tests - 65 passed, 9 failed (6 overflow panics at `i64::MAX`/`i64::MIN`, 2 restarts crediting past `now_at`, and the pinned anomaly timing). Then fixed in `a2fbaff`. RED evidence round 3: commit `2d19a92` added the record-cap and voice zero-id tests - 8 failed, and one of them ABORTED the test binary (`memory allocation of 171798691840 bytes failed`, STATUS_STACK_BUFFER_OVERRUN) because the day split asked for one record per UTC day across the whole `i64` range; the other 7 failed on their assertions. Then fixed in `d7a945b`. Commit `0eb8c3e` added the two tests that close the coverage gaps the round-3 battery found.
Mutation evidence: 42 deliberate mutations across the three rounds were each caught by a named test. Round 2 ran 26 - the day floor, the day start and next day start overflowing, the midnight split, the AFK and self-deaf guards, the bot, excluded-channel and zero-id checks, the out-of-order guard, the five anomaly kinds, the credited user id, start, end and seconds, and the restart end (heartbeat only, restart only, the later of the two). Round 3 ran 16 - the cap not firing, the cap off by one, the cap refusing everything, the record count always zero, the record count reading only the last stretch, the day count off by one, the day count of an empty stretch, the refusal raising no anomaly, the refusal not returning, and the guild, user, channel, old-channel and new-channel zero checks dropped one at a time. Two of the round-3 mutations SURVIVED the first pass (the record count reading only the last stretch, and the day count of an empty stretch); both were gaps in the SUITE, not in the code, and two tests now pin them (`a_session_split_into_stretches_counts_every_stretch_against_the_cap`, `an_empty_stretch_does_not_count_against_the_cap`). One mutation SURVIVES from round 2: changing the day-split step from `cursor.saturating_add(1)` to `cursor + 1` is behaviour-identical, because the cursor is always below the end of the session and the end is an `i64`, so the step cannot overflow; the property the guard protects (`next_day_start` is after every cursor the split can take) is pinned by `the_next_day_start_is_after_every_cursor_the_day_split_can_take`. The guard is a backstop, not a behaviour.

NOT done: no runtime, no Discord registration, no commands, no event wiring, no `.env`/`config.rs` change, no persistence (the increments and sessions are plain data for AC2), no heartbeat source (the caller passes the last heartbeat in), no XP or stats logic. The module-level `#![allow(dead_code)]` in `src/activity/mod.rs` is temporary and wiring card W1 removes it.
