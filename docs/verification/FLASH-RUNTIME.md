# FLASH-RUNTIME - flash-media runtime (FL2)

`src/flash/runtime.rs` and `config.rs` run the flash-media feature on top of the pure policy (FLASH-POLICY.md). Discord is behind two traits (`FlashPorts`, `StaffAlerter`); deletions go through `crate::jobs`. `FlashFeature` implements the registry `Feature` hook but is NOT registered (`production_features()` is still empty; a test checks it).

Rules enforced (each has a test):
- Live: schedule `flash_delete_source` (due now+delay, key per message id) BEFORE posting the notice, then post, then schedule `flash_delete_notice` (same due time, key per notice id). The plan says post-then-schedule; scheduling first means a crash in between cannot leave the media without a deletion. A notice failure alerts and keeps the source job; a source job that cannot be scheduled posts no notice (alert). A replayed event (same key) posts no second notice.
- Both kinds are `RunAgain` (PLAN 5.7). The card text says AtMostOnce for irreversible work, but a delete is idempotent and AtMostOnce would abandon a cut-off or overdue delete. Plan wins. Overdue jobs run at once after a restart; a job left `running` is requeued.
- Delete: 404 = done. 403 = alert `flash_delete_forbidden` and a failed attempt; any other error = alert and a failed attempt. The handler API has no terminal fail, so the queue retries with its back-off until its max attempts, one alert per attempt, then the job is `failed`. The plan wants 3 bounded tries, no loop on 403 and deduplicated alerts; that needs a terminal handler error in the job runner, so enabling live requires KJ3 (jobs-lane follow-up card).
- Shadow: no send, delete, alert or job; it only reads (thread parent) and counts (`shadow_summary`). It reports `needs_core_db() == false`, so no database and no job kinds. Off does nothing.
- Payloads hold ids only and are parsed strictly (object form, exactly two keys, non-zero). Alerts are `flash alert: <code>`. Notice mentions are the policy's (role, author, never everyone).
- A flash event does not reach the cache or logger: tested through the real `route_event` and cache insert with the flash ids in a `LogExclusion::Scope` (what W2 must build); a control case shows it would be cached without them.

Tested: 59 new tests (14 config, 45 runtime): pure helpers, `process` in every mode, the handler, a real `Runner` with a fake clock on a file DB (overdue after restart, crash requeue, 179/180 s boundary, 404, 403, transient), registry routing, and a seeded liveness test (12 LCG seeds x 60 steps of flashes, Discord faults, crashes). RED `32eae46`: 56 failed, 2 passed (they only read constants). Mutations that made tests fail: 404 not done, source AtMostOnce, due off by one, shadow acting, array payload accepted, duplicate re-posting, shadow needing the db, no wake, mode ignored, lenient flag, 403 done, default delay, first-of-many role, missing alerts, unknown parent proceeding, `everyone` mention, zero message id, source job not scheduled. Round 2 (tests only, commit `3f99ca2`, which passes on the unchanged code): one test pins the Off/inactive gate (flash channel, other channel and thread, in `off` and in `live` with empty channels: `Outcome::Off` and no port call), and the liveness model now answers an already-gone message with a persistent 404 and checks `done`, one delete call, no extra attempt beyond crash-lost claims, and `DeleteFailed` alerts only for scripted transient faults. The surviving mutants before the fix: the gate replaced by `if false`, and 404 mapped to a failed attempt (the old one-shot 404 let the retry succeed). Both now fail (the second in the liveness test alone).

Config keys (read by the wiring card, not here; a bad value switches the feature OFF and the error names only the key): `FLASH_MODE` default `off` (typos = off, no error); `FLASH_CHANNEL_IDS` default empty = inactive; `FLASH_PING_ROLE_ID` default unset = no role mention (a list or 0 = off); `FLASH_DELAY_SECS` default `180`, `10..=86400`; `FLASH_INCLUDE_THREADS` default `true`, exactly `true`/`false` (K06 has no boolean helper, so this one has a strict local parser). `GUILD_ID` is passed in by the caller.

NOT done: not called from `main.rs`, no command, nothing switched on, no `.env.example` line. `SerenityFlashPorts` (HTTP, cache, staff alert post) has never run against Discord; only its status mapping is tested. Flash ids are not yet in the log exclusion scope (W2). A flash posted while the bot is down is never seen (no history scan). Switching live to shadow/off with jobs pending leaves them unrun. An unresolvable thread parent is ignored without an alert. Live with no core database raises `SourceNotScheduled` for every flash (the media stays up, alert only). A crash between the notice post and its job scheduling leaves an orphan notice. W2 must build the log-exclusion `Scope` with the flash channel ids.
