# Safeword State Machine (SW1)

Pure, Discord-free state machine (`src/safeword/{mod,state}.rs`) replacing the YAGPDB safeword custom command.

## Rules Enforced
- **Activation & replay safety:** Snapshots `held_roles ∩ restricted_roles`, removes them, adds the safeword role if not held, and DMs verbatim text. Replayed `ReactionAdded` while `Activating` or `Active` never overwrites the snapshot (fixes YAGPDB line 68 bug).
- **Restore filtering (D06):** By default (`filter_restore = true`), release skips roles struck via `Strike(role)`, deleted via `RoleDeleted(role)`, or present in `protected_roles`; setting `filter_restore = false` restores all originally saved/deferred roles.
- **Deferred grants (D06):** When `defer_grants = true` (default), `GrantDuringActive(role)` records the role into the snapshot for restore on release. In `Releasing`, while `RestoreRoles` has not been acknowledged, a grant of a restricted role is deferred and added to `restore_plan` (subject to the same struck/deleted/protected filters); once `RestoreRoles` is acknowledged the member is no longer restricted (safeword role removed first), so a later grant is ignored.
- **Last-reaction-event-wins & crash recovery:** `ActionDone(id)` / `ActionFailed(id, code)` track per-step progress (including unacknowledged steps in `Active`) so retries never repeat completed actions. In `Activating`, `ReactionRemoved` sets `pending_release` (completes activation then releases) and a later `ReactionAdded` clears it so the member ends `Active`; duplicate or out-of-order replays are reconciled by the runtime via `restart_action(state, reaction_present_now)`.
- **Re-add during `Releasing` (`pending_reactivate`):** `ReactionAdded` in `Releasing` sets `pending_reactivate` (cleared by a later `ReactionRemoved`); when release completes with `pending_reactivate` set, `step` continues straight into a fresh `Activating` snapshot from `ctx.held_roles` (which the runtime must supply current at that event) and emits its activation actions.

- **At most ONE RestoreRoles in flight (round 4):** `restore_in_flight` (bool) + `last_emitted_restore_plan`. A grant emits `RestoreRoles(plan)` only when none is in flight; otherwise it grows `restore_plan` and emits nothing (late grants coalesce). On `ActionDone(RestoreRoles)` the machine clears in_flight and, if `restore_plan != last_emitted_restore_plan`, emits ONE follow-up and stays `Releasing`; the release closes only after an ack whose payload equals the current plan. On `ActionFailed(RestoreRoles)` it clears in_flight. **Retry (round 5):** every failure joins `failed_steps` (a set, so a later failure never forgets an earlier one, in `Releasing` and `Activating` alike); a retry trigger (`ReactionRemoved`/`ReactionAdded`, or `restart_action` -> `Trigger`) with any failed step re-emits EVERY unacknowledged step, each once, and `RestoreRoles(current plan)` only if none is in flight. `last_failure` is informational only (what failed last, for logging), never a gate. Runtime contract: the runtime executes SW1's actions of the same ActionId one at a time, in the order emitted, and reports each outcome once; an `ActionDone/Failed(RestoreRoles)` with nothing in flight is stray and ignored. SW2 wiring: snapshots persisted by an older build deserialize with `restore_in_flight=false`. A grant deferred before re-activation is applied by RestoreRoles, not carried into the fresh snapshot; the runtime must pass CURRENT held roles on the re-activation event or the member is left unprotected. In `Active` only `SaveSnapshot` can be pending, so only its failure is recorded.

## Config Keys (Read by Wiring / SW3, Not Here)
- `SAFEWORD_MODE` (default `off`; any value other than `off|shadow|live` fails closed to `off`).
- `SAFEWORD_ROLE_ID`, `SAFEWORD_CHANNEL_ID`, `SAFEWORD_MESSAGE_ID`, `SAFEWORD_EMOJI_ID` (default `""`; missing/invalid ID fails closed and disables safeword).
- `SAFEWORD_RESTRICTED_ROLE_IDS`, `PROTECTED_ROLE_IDS` (default `""`; comma-separated role IDs; invalid entries rejected/fail closed).
- `SAFEWORD_DM` (default `true`; invalid fails closed to `true`), `SAFEWORD_DEFER_GRANTS` (default `true`; invalid fails closed to `true`), `SAFEWORD_FILTER_RESTORE` (default `true`; invalid fails closed to `true`).

## What Is NOT Done
No Discord runtime, no slash commands, no SQLite persistence (SW2), and no wiring beyond `mod safeword;` in `src/main.rs`.
