# WELCOME-RENDER - welcome template and renderer (pure)

Card WE1. Module `src/welcome/{mod,render}.rs` - pure, Discord-free core.

`welcome::render::WelcomeTemplate::load(&str, &IdMap)` parses and validates one JSON template (one embed plus optional content). `welcome::render::welcome_policy(&MemberContext) -> SkipReason` decides whether a joining member is skipped. `welcome::render::render_welcome(&WelcomeTemplate, &MemberContext, &IdMap) -> RenderedWelcome` fills the placeholders and returns plain data (content, embed title/description/fields/footer/author, and a `truncated` flag). No serenity type, no I/O, no clock read, no randomness; every id, the member count and the server name are passed in.

Rules it enforces:
- An unknown placeholder, an unknown `{channel:KEY}` / `{role:KEY}` key, a malformed key and an unbalanced brace are refused when the template is LOADED, never when a member joins. A `{}` with an unknown JSON key is refused too. `{user_mention}`, `{username}`, `{server}`, `{member_count}`, `{member_ordinal}` (1st, 2nd, 3rd, 11th, 12th, 13th, 21st, 111th ...), `{channel:KEY}`, `{role:KEY}`.
- The untrusted `username` is stripped of zero-width and bidi control characters, escaped against Discord markdown and neutralised against mention syntax (`@` becomes the full-width `＠`, `<` and `>` become `‹` and `›`), and the RESULT is then capped at 64 characters, so the escaped name is never longer than the cap. The caller-supplied `server` name is stripped of control characters, neutralised against the mention syntax and capped at 100 characters; its markdown is NOT escaped, because the server owner chose that name. `{user_mention}` is the only way a user mention is produced; `{channel:KEY}` and `{role:KEY}` carry an id from the caller's map, so the only id the renderer emits is the joining user's own id and the ids the caller put in the map. The caller must pass the SAME map to `load` and to `render_welcome`: a key missing from the render-time map renders as an empty string, because a missing id never fails a join.
- The Discord embed limits are checked on the TEMPLATE TEXT at load and count characters, not bytes: title 256, description 4096, at most 25 fields, field name 256, field value 1024, footer 2048, author name 256, 6000 characters in total (title + description + every field name and value + footer + author). The message content limit is 2000 characters. An empty field name or value is refused; a field name or value that is not a string is refused as malformed.
- A placeholder EXPANDS at render time, so the template text being inside the limits does not mean the rendered text is. The renderer clamps the RENDERED result to the same limits: each slot is shortened to its own limit, then the embed is shortened until its total fits 6000 characters - the description first, then the footer, then the last field's value and name (a field that cannot keep both is dropped), then the author name, then the title. The cut is on a character boundary. When something was cut, `RenderedWelcome::truncated` is true.
- A bot member is skipped (`SkipReason::Bot`); a human is `SkipReason::None`. The old YAGPDB command welcomed bots as well; that is deliberately not copied.
- The id map keeps channels and roles apart, refuses the id zero and a key that is not a plain word, and keeps the first id inserted for a key.
- Errors are stable enum codes (`TemplateErrorKind::code()`, 21 of them); they never carry template text, a user name or an id.

Config key (read by the wiring card, not by this module): `WELCOME_TEMPLATE_PATH`, default unset. Unset means the welcome feature is off. The required safe failure for the wiring card: a path that cannot be read, or a template that fails to load, must leave the welcome unposted and the startup message must name the key, never the template text. This module reads no environment variable and no file, so it enforces none of that itself.

Tested (92 unit tests in `src/welcome/render.rs`): the example template loading and rendering with no leftover placeholder; every placeholder substituted; the ordinals including the teens and the 100/1000 boundaries; an unknown placeholder, an unknown channel key and an unknown role key refused at load; a hostile key refused at load (empty, space, dash, dot, slash, a path, a `file://` URI, a `$(...)` shell fragment, a non-ASCII letter, a brace, a wrong kind of thing and a doubled prefix) and an unbalanced or doubled brace refused at load; the unknown JSON field refused; the username escaped against markdown, `@everyone`/`@here`, user and role mention syntax, zero-width and bidi controls, capped at 64 characters by characters not bytes, and escaped in every place it can appear; the server name capped, mention-neutralised and control-stripped; every embed limit at its exact value (256/257, 4096/4097, 25/26 fields, 1024/1025, 2048/2049, 6000/6001) and the multi-byte variant; the 2000/2001 content limit; the empty and the malformed field name and value; the bot skipped and the human not skipped; the id map rules; the error-code table, the error text carrying no template text, and the error being a `std::error::Error`. The RENDERED limits are tested too: a template that CONTAINS placeholders is rendered and the rendered description, field value, content, field name, footer, author name, title and embed total are measured against the limits - for a repeated placeholder, for a long server name, and for the worst-case member (the longest name, the longest server name, `u64::MAX` ids); the clamp cuts exactly the excess, cuts the description before the footer, never leaves a field without a name or a value, keeps the whole limit in characters (never half a code point) and always finishes.

RED evidence: commit `587fdfe` ran the suite against a non-functional scaffold - 11 passed, 51 failed (the 11 were already satisfied by the type definitions alone). Round 2 RED evidence: commit `ee07e86` added the rendered-limit tests and ran them against the round-1 implementation - 64 passed, 8 failed, reproducing the reviewer's probe numbers (description 4150 > 4096, field value 1078 > 1024, content 2054 > 2000, a repeated placeholder 25600 > 4096, a long server name 5000 > 4096, the sanitised username 128 > 64).

NOT done here: no runtime (nothing posts a welcome, grants a join role or reacts to a join event); no Discord registration, commands, event wiring or `.env`/`config.rs` change; no persistence and no database table; the join roles are the role-service card's work, not this card's; the module-level `#![allow(dead_code)]` in `src/welcome/mod.rs` is temporary and W3 removes it.
