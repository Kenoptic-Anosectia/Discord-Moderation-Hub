# MANAGED-EMBEDS - managed embed posts (pure core)

Card EM1. Module `src/embeds/{mod,template,posts}.rs` - pure, Discord-free core. This card IS the persistence card for the `managed_posts` table.
`embeds::template::load(&str) -> Result<EmbedTemplate, TemplateError>` loads one embed template from JSON, checks it against the Discord embed limits and returns it trimmed. `EmbedTemplate::content_hash()` is the SHA-256 hex digest of the canonical form of the PARSED template, so the JSON key order of the source file cannot change it. `embeds::posts::plan(&PlanRequest) -> Plan` decides create / edit / no-op / recreate / refuse. `embeds::posts::{migrate,get,upsert,apply,list,delete}` read and write the `managed_posts` row; `upsert` is the raw write and looks at no plan, so the wiring card should write through `apply`. No serenity type, no clock read, no randomness; `now` is a parameter and every id is passed in.

Rules it enforces:
- Same template twice -> `NoOp` (reposting would spam the channel). Changed template -> `Edit` of the SAME recorded message, never a new post.
- A recorded message reported missing -> `Refuse(missing_message)`, or `Recreate` only when the caller passes the explicit allow-recreate flag (a deleted rules post may be deliberate). A key recorded for another channel or another guild is refused; the allow-recreate flag does not lift that refusal.
- `apply` checks the record against the plan before it writes: an `Edit` for another message, or a write that moves the guild or the channel, is refused with `plan_mismatch`; a `Create` over a row that already exists is refused with `already_exists` (a plain INSERT, not an upsert). A `Plan::NoOp` or `Plan::Refuse` writes nothing.
- A key has ONE canonical spelling: lowercase ASCII, starting with a letter or a digit, then letters, digits, `-` or `_`, at most 64 bytes, and not a reserved Windows device name (`con`, `prn`, `aux`, `nul`, `com0`-`com9`, `lpt0`-`lpt9`). A case alias would name the same template file twice on a case-insensitive file system. A template hash that is not 64 lowercase hex characters is refused too.
- Limits, inclusive, measured in characters after trimming: title 256, description 4096, 25 fields, field name 256, field value 1024, footer text 2048, author name 256, and a combined total of 6000 over title + description + every field name + every field value + footer text + author name. A field whose name or value is empty after trimming is refused (`field_name_empty` / `field_value_empty`): Discord rejects such a field. An unknown JSON key, a duplicate JSON key, a non-object document, a colour above 0xFFFFFF and a template with no content are refused too.
- Every error and refusal is a stable code. No error, `Display` or `Debug` output ever contains template text, a field name or a value.

Config keys (read by the wiring card, not by this module), default then safe failure: `EMBED_TEMPLATE_DIR` unset, unset => the feature is off and no template is loaded; this module reads no environment variable and no file.

Tested (82 unit tests in `src/embeds/{template,posts}.rs`): the General and NSFW rules embeds rebuilt from `YAG:199-248` load within the limits (the NSFW one is 5 fields, 3458 characters in total, every field value under 1024); each limit at and one past the boundary; the total counted over every part; whitespace trimmed before measuring; empty text normalised to absent; an empty or whitespace-only field name or value refused; colour 0 and no colour hashed differently; a duplicate JSON key refused; the twelve error codes distinct and stable; no template text in an error; the hash 64 hex characters, stable across JSON key order, changed by content, by field order and by colour; the canonical form unambiguous; the planner create / no-op / edit-same-message / missing-refused / missing-recreate / key-reuse cases, plus the allow-recreate, invalid-key and invalid-hash refusals; the planner pure; the migration idempotent; the repository round trip, replace, survive-reopen, ordered list, delete, corrupt-id, corrupt-hash, non-canonical-id, unusable-stored-key and zero-id reporting; the plan guarding the write; the plan and the record agreeing; an `Edit` or `Recreate` for a key with no row refused. Two seeded LCG sequences (600 steps each) drive the real `plan` and `apply` against a model runtime that changes the template, deletes the post, fails the Discord call and loses the record write: the module settles into `NoOp`, an edit never targets a message that does not exist, and the live posts stay within the duplicate window named below. RED evidence: commit `bf8de90` (round 1) ran the first suite against a non-functional scaffold - `test result: FAILED. 9 passed; 43 failed`; commit `5660c94` (round 2) ran the new tests against the old behaviour - `test result: FAILED. 61 passed; 19 failed`. Mutation evidence: round 1, 23 one-condition mutations each caught by a named test; round 2, 17 mutations - 15 caught by a named test, and the 2 that survived were REDUNDANT defences (a `Create` over an existing row is refused by the primary key of the table AND by an explicit check, so disabling one at a time changes nothing; disabling both at once is caught).

NOT done here: no runtime (nothing posts, edits or schedules); no Discord registration, no commands, no event wiring, no `.env`/`config.rs` change; the module reads no environment variable and no file; no rendering to a serenity `CreateEmbed` (the wiring card EM2 builds that); the module-level `#![allow(dead_code)]` in `src/embeds/mod.rs` is temporary and W1 removes it.

Limit that is NOT closed here: a post that succeeds on Discord and whose record write then fails leaves the table without a row, so the next sync plans a `Create` again and a second copy of the post is made. The window is between the post and the record of it. This module cannot close it; the wiring card can shorten it. The write of `apply` is a read followed by a write, not an atomic compare-and-swap, so two writers of the same key can still race.
