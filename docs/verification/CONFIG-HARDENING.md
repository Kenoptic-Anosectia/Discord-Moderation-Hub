# CONFIG-HARDENING

Card SF3 (audit MEDIUM/LOW), base `13a1764`. All three findings reproduced.
**1. Env precedence — FIXED.** `main.rs` used `dotenvy::dotenv_override()`, so a stale `.env` beat an exported variable. `config::load_env()` now calls `dotenvy::dotenv()`: the real environment wins, only variables the environment does not hold come from the file. Test `env_file_does_not_override_the_real_environment` exports `SF3_REAL_ENV_SENTINEL=from_environment` while the file sets `from_file`; the exported value must survive and a file-only variable must still load. RED (round 1): `left: Ok("from_file")`, `right: Ok("from_environment")`. Behaviour change: anyone who relied on `.env` overriding the environment is affected; Ava's no-exports setup is not.
**1b. Search delegated — FIXED.** The hand written `find_env_file` walk used `Path::is_file`, which answers `false` for *every* metadata error and so kept walking up when a candidate could not be read: the bot silently loaded a different `.env`. The walk is deleted and `dotenvy::dotenv()` does the search; dotenvy stops with an error on a non-`NotFound` metadata error. Test `load_env_finds_the_nearest_file_above_the_working_directory` drives a child process with its own working directory and asserts the loader returns the file dotenvy finds; `load_env_fails_closed_when_the_environment_file_cannot_be_used` asserts a broken nearest file is an error and that no other file is loaded instead.
**2. `Config` Debug leak — FIXED.** `Config` derived `Debug`, so `{:?}` printed `discord_token` verbatim. A manual impl prints `<redacted>` for the token, keeps every other field, and takes the struct apart without a rest pattern, so a field added later does not compile until it is listed and a decision is made about it. Test `config_debug_output_never_contains_the_token` checks the token never appears and non-secret values still do; `config_debug_output_lists_every_field` checks no field is dropped. RED: derived output printed `discord_token: "synthetic-token-must-never-be-printed"`.
**3. `LOG_CHANNEL_ID=0` — FIXED.** Read with `required_u64`, so `0` was accepted. Now `required_discord_id`: a Discord id is a non-zero u64, so `0`, negatives and non-numeric values are rejected and the configuration does not load — the existing safe failure, the bot refuses to start. Test `log_channel_id_must_be_a_valid_discord_id` runs a child process per case (`0`, `-1`, `not-a-number`, unset, valid id) and loads only for the valid id. RED: the `0` case loaded. A rejected value fails with `ConfigValueError { key, code }` using the stable `ConfigValueCode::InvalidDiscordId`, never the value itself.
**NOT fixed / limits.** `AGE_ROLE_1`/`AGE_ROLE_2` still load `0`, but `0` is refused at use by `valid_role`, and `STAFF_ROLE_ID` `0` is filtered by `parse_staff_role` and rejected by `Settings::valid`, so `0` is not harmful there and nothing was extended. `+123`, leading zeros and ids above `i64::MAX` are still accepted; that matches the old `required_u64` and does not panic. An exported but empty `LOG_CHANNEL_ID=` now wins over the file and the bot refuses to start: correct `dotenv()` semantics. The token is still a plain `String` cloned into `main`; only `Debug` is redacted, and `Config` has no `Serialize`. The search test covers the loader, not a full start-up. `.env.example` not edited; proposed line: `# The real environment wins over this file; LOG_CHANNEL_ID must be a real Discord id.`
