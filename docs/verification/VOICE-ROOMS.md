# VOICE-ROOMS - temporary voice room policy (pure)

Card VR1. Module `src/voice_rooms/{mod,policy}.rs` - pure, Discord-free core, no serenity type, no I/O, no clock read, no randomness; `now` and every id are passed in.

## Rules enforced
- **Hub join creates a room** (`decide_join`): only a join in the hub channel of the configured guild, by a non-zero user id, and only under the per-user cap, the global cap and the per-user cooldown. Each refusal carries a stable code (`per_user_cap_reached`, `global_cap_reached`, `create_cooldown`, `not_hub_channel`, `invalid_user_id`, `guild_mismatch`).
- **Name sanitising** (`sanitize_name`): the cleaning runs in a fixed order - the invisible characters FIRST, then the mentions until the text stops changing, then the links. Removing the invisible characters first is what stops a zero-width character from hiding a mention from the mention pass; running the mention pass to a fixed point is what stops a nested token from reassembling into a live token. The invisible class is a class, not a list: the format characters that hide text (the zero-width characters, the bidirectional controls U+202A-U+202E, the isolate controls and the tag characters U+E0000-U+E007F), the Hangul filler and the non-ASCII spaces; the plain ASCII space is kept. A link is a class too: a segment whose host part (in front of the first slash, question mark or fragment marker, without the port and without the user information) is a dotted name whose last label is alphabetic or punycode is a host, so `example.com`, `example.com:8080/x`, `example.com?x=1`, `example.com.`, `(example.com)`, `www.x.y`, `example.xn--p1ai` and `discord.gg` are removed, as are URLs, invite hosts and an invite host spread across spaces (`discord . gg/x`). Shortens to at most 100 characters (characters, not bytes) and falls back to the default name when nothing is left.
- **Overwrite plan** (`build_overwrites`): the category's overwrites plus one owner overwrite. The owner's allow set is the constant `OWNER_RIGHTS` (connect, speak, move, mute); the deny set is `FORBIDDEN_OWNER_RIGHTS` (manage roles, manage channels, administrator). No input can widen the owner rights.
- **Permit** (`decide_permit`): refused when the member could not already view the category, when a member id is zero, when the requester does not own the room, when the member is the owner themself, and in a channel the policy does not track.
- **Leaving** (`decide_leave`) and the **sweep** (`decide_sweep`): the owner leaving a room that still holds members makes it `Claimable`; an empty room becomes `Cleanup` only once the grace period has elapsed. The grace check comes first and applies to whoever leaves last, so a room whose owner already left is still cleaned up; only a member leaving a room that still holds members can be refused for not being the owner. A channel the policy does not track is never deleted. The sweep is the runtime's periodic check for a room whose last member left before the grace elapsed, so nobody leaves it again: it cleans an empty room up once the grace has elapsed, never touches an occupied room, never claims a room and never touches an untracked channel.
- **Rename budget** (`decide_rename`): counted per room inside its window; the budget is data, so the runtime enforces the same number. Discord's exact limit is not verified here.
- **Time is injected and never overflows**: every elapsed time uses `saturating_sub`, so an extreme value loaded from persistence can neither panic in a debug build nor wrap around in a release build. A negative grace period or a negative rename window is refused with `invalid_config` rather than honoured.

## Assumptions (Chai's behaviour is unknown; conservative where silent)
- The room name at creation is the configured default; `sanitize_name` is also the public entry point for a later rename command. The guild id is part of the configuration: a join from another guild is out of scope.
- The exact Discord rename limit is not verified; the budget is data with a default of 2 renames per 600 s. Discord retired `MANAGE_PERMISSIONS`, so serenity 0.12 has no constant for it; the escalating set is manage roles, manage channels and administrator, and the retired bit is named `LEGACY_MANAGE_PERMISSIONS` so it can be asserted on.
- The occupancy is the count BEFORE the leave: a room with one member left is empty, a room with two is not. The runtime owns the count and the `empty_since` stamp; the policy reads them and never writes them.

## What is tested (98 unit tests in `src/voice_rooms/policy.rs`)
Hub join creates a room and each cap, the cooldown and the channel/guild/id checks deny; the cooldown boundary is allowed exactly at the limit; every sanitising case above, including a mention split by a zero-width character, a joiner or a control character, a nested mention token, a name of only invisible characters, a host in brackets, a host with a comma, a trailing dot, a query, a fragment, angle brackets and a punycode top-level domain; the owner overwrite grants exactly the four rights and grants none of the escalating ones (the category's own overwrites are copied through unchanged, so what the server admin put there is what the room gets); the permit refusals; owner leave -> claimable, empty -> cleanup only after the grace, the grace boundary, untracked channels never deleted; a non-owner leaving an empty room still reaches the grace check; the sweep cleans an empty room up after the grace, never an occupied one, never an untracked one and never claims one; the rename budget, its per-room count, its window and the "never plans more renames than the budget" loop; the five extreme-timestamp cases; the negative grace and the negative rename window are refused; a seeded 2000-step join/leave sequence that asserts the global and per-user caps after every step; a second seeded sequence whose quiet phase drains the rooms, advances the clock past every grace and asserts that every room is actually GONE from the state.

**RED evidence:** commit `6fec05c` ran this suite with the decision functions unimplemented - `test result: FAILED. 11 passed; 45 failed`. ## Config keys (READ by the wiring card, not by this module; this module reads no environment variable and no file)
`VOICE_ROOMS_MODE` (default `off`; any other value means off) | `VOICE_ROOM_HUB_CHANNEL_ID` (default unset; unset means no hub, so no room is ever created) | `VOICE_ROOM_CATEGORY_ID` (default unset; unset means no category, so no room is ever created) | `VOICE_ROOM_PER_USER_CAP` (default `1`; invalid or negative means 1) | `VOICE_ROOM_GLOBAL_CAP` (default `25`; invalid or negative means 25) | `VOICE_ROOM_CREATE_COOLDOWN_SECS` (default `30`; invalid or negative means 30) | `VOICE_ROOM_EMPTY_GRACE_SECS` (default `60`; invalid or negative means 60 - a negative grace would clean a room up the instant it became empty) | `VOICE_ROOM_DEFAULT_NAME` (default `Voice Room`) | `VOICE_ROOM_RENAME_BUDGET` (default `2`) | `VOICE_ROOM_RENAME_WINDOW_SECS` (default `600`; negative is refused by the policy as `invalid_config`, because a negative window would make the rename budget unlimited).

## What is NOT done
No runtime (nothing creates, deletes, renames or permits), no Discord registration, no commands, no event wiring, no persistence, no `.env` or `config.rs` change. The module-level `#![allow(dead_code)]` in `src/voice_rooms/mod.rs` is temporary and wiring card W1 removes it. The state (`VoiceRoomState`) is plain data the runtime owns; nothing here writes it. The occupancy count and the `empty_since` stamp are the runtime's to maintain: the policy reads them and never sets them, so a runtime that does not stamp `empty_since` never cleans a room up.
